# 我的数模Prompt方式

这份流程按作者明确提供的实际提示整理。队号、路径用占位符；不添加作者未说过的实验预算或统计指令，也不将助手执行中的技术检查包装成作者的prompt。

## 先建立协作规则，再按问题推进

| 阶段 | 作者提示的主要内容 | 助手负责落实的工作 |
|---|---|---|
| 1. 初始化 | 初始化git、每次对话后更新；队号不硬编码；工作文档以题目为标题；题目专用要求；AGENTS | 建立持续记录与版本管理，分离运行配置，保存题目流程 |
| 2. 理论审查 | 专注问题1和问题2；是否最优、自洽；有没有漏洞；后续写论文 | 审查假设与目标，给推导、证明、反例或修正 |
| 3. 代码与大纲 | 基于这个完善代码，维护论文大纲 | 落实理论结论，验证程序，建立论文映射 |
| 4. 后续问题 | 基于前两问完善后两问；优先官方接口；能否自动化并迭代 | 核对新增条件和接口，在授权范围内验证真实系统 |
| 5. 外部review | 看其他AI对原始idea的review有没有值得完善的地方 | 独立核验建议，采纳有依据的改动 |
| 6. 详细理论 | 整个问题的推导越详细越好；附权威来源；对齐不确定处和论文；彻底解决理论问题 | 完整论证、关闭能修复的缺口，说明尚未证明的边界 |

这不是一次超长prompt，而是在项目中逐步提出要求。随后不断给新的review、继续改进，并对论文做微调。各阶段可回退；例如代码验证发现理论缺口，就回到推导。

## 这种方式的特点

**用自然问题提出目标。** “是否已经最优了”“有没有漏洞”是审查请求，用户不必先把优化空间、反例搜索或实验设计写成技术规范，助手应主动完成必要分析。

**用文件持续承接。** 工作文档、AGENTS、论文大纲和详细推导保存决定、依据和进度，Git每轮记录相关改动。新会话靠文件续接，不依赖聊天永久完整保留。

**把review作为迭代输入。** 其他AI的review提供疑点和候选建议，助手核验后决定是否采纳；review不是自动正确的答案，更不能替代证明。

**要求理论、代码和论文互相对齐。** 从审查到代码改进，再到详细推导和论文，避免论证留在聊天、程序采用另一套逻辑或论文写未部署方法。

**用短句调整当前工作。** “继续”“目前先不用改动论文”“做最小修改”沿已有上下文生效。限制和用户原有修改须保留，不要求每轮复制完整提示。

## 如何复用

安装后首次加 `使用 $cumcm-modeling`，按 [六类调用示例](prompt-examples.md) 提供材料与当前目标。将具体题目的测试、数据或运行方式写入项目AGENTS；无模拟器的题目省略接口分支。

助手应根据任务补全技术核验，并如实说明结果与边界；不要要求用户模仿专业术语、虚构固定时限，或把“彻底解决”转成无法证实的最优承诺。

论文起点见 [LaTeX模板](../../latex-template/README.md)。正文根据真实推导与实验填写，模板教学内容不是比赛结果。
